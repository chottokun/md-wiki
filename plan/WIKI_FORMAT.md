# Wiki Format Definition & Aesthetics (ナレッジ構造と審美性定義)

本ドキュメントは、md-wiki プロジェクトにおける Markdown ファイルの物理構造、メタデータ規格、および視覚的・構造的デザインの指針を定義する。エージェントは執筆・更新時に本定義を「正」として参照し、一貫性を維持しなければならない。

---

## 1. ページ構造 (Page Anatomy)

Wiki ページは以下の 4 つの主要ブロックで構成される。

### 1.1. YAML Frontmatter (Properties)
Obsidian で「プロパティ」として認識されるメタデータ領域。OKF v0.1 に準拠し、`WikiFrontmatterSchema` に準拠する。

- **`type` (必須)**: 概念の分類。`Concept` (技術用語), `Article` (統合記事), `Source` (一次ソース), `RawSource` (解析テキスト), `Reference` (外部参照), `Landscape` (俯瞰)。
- **`title` (推奨)**: 表示用の人間が読めるタイトル。
- **`description` (推奨)**: 
  - 恒久ページ: 1〜3行程度の具体的要約（旧 `abstract`）。
  - スタブ: `(自動生成スタブ: 本文の内容に基づき後日更新予定)`。
- **`resource` (推奨)**: 外部の正規の資産URI。
- **`tags` (推奨)**: 
  - 必須: `未審査` (新規・更新時)。
  - その他: 技術分野、モデル名、タスク名など。
- **`timestamp` (推奨)**: 最終更新日時 (ISO 8601 `YYYY-MM-DDTHH:MM:SS+09:00` 形式、旧 `updated`)。
- **拡張 (Producer-defined)**:
  - `aliases`: タイトルの「完全な別名」または「略称」。
  - `concepts`: 本文中の主要概念リスト。
  - `created`: 作成日時 (ISO 8601)。
  - `sources`: 引用元へのリンクリスト `[[sources/filename.pdf]]`。

### 1.2. Abstract Callout (要約)
ページ冒頭に配置される視覚的な要約（md-wiki 固有の拡張）。

- **形式**: Obsidian の `[!abstract]` コールアウトを使用。
- **内容**: 
  - 恒久ページ: 記事の核心を突く要約（`description` の内容と同期）。
  - スタブ: `(自動生成スタブ)`。

### 1.3. Main Content (本文)
Markdown 形式の技術解説。

- **H1見出し**: `# タイトル`（ファイル名と一致させる）。
- **セクション構造**: `## Overview`, `## 💡 主要な概念` 等。
- **内部リンク**: 専門用語は積極的に `[[用語名]]` でリンク化する。
- **視覚要素**: 複雑な比較には「Markdownテーブル」、手順には「箇条書き」を多用する。

### 1.4. Citations (リソース引用 - OKF §8)
- **`---` (水平線)**
- **`# Citations`**: 一次ソース (`sources/`) や原文 (`raw_markdown/`) へのリンク、または外部Webサイトへの参照。
- **推奨**: Wiki の最下部に配置。

## 2. ページタイプ別ガイドライン

### 2.1. 知識統合ページ (Integrated Wiki)
PDF等のソースから抽出・統合された恒久的なナレッジ。
- **デザイン目標**: 専門書のような密度と読みやすさの両立。
- **必須セクション**: `## 概要`, `## 💡 主要な概念`。

### 2.2. 自動生成スタブ (Concept Stub)
Red-link 検知により自動起票された未完成ページ。
- **デザイン目標**: 最小限の定義と、広範な関連リンクの提供。
- **メタデータ**: 
  - `abstract`: `(自動生成スタブ: 本文の内容に基づき後日更新予定)`
  - 本文内要約: `(自動生成スタブ)`
- **特徴**: LLM の内部知識または Qdrant からの断片的コンテキストに基づき構成される。

## 3. 審美性と可読性の原則 (Aesthetics)

1. **プレースホルダーの排除**: 「要約なし」等の無機質な表現を避け、スタブであっても「次に何が起きるか」を予感させる表現にする。
2. **構造的視認性**: 
   - 段落は短く保つ。
   - 重要なキーワードは太字 (`**bold**`) を適宜使用。
   - 表形式 (`| column |`) を積極的に使い、データの比較を容易にする。
3. **リンクの密度**: 1つのセクションにつき、少なくとも 2〜3 個の内部リンクを含めることを目指す（ナレッジグラフの強化）。
4. **人間による考察の尊重**: `## 💡 人間の考察` セクションは、AIが自動生成する領域とは別に、人間が自由に思考を記述できる聖域として保護される。

---

## 4. 考察と今後の課題

- **スタブの格上げフロー**: 自動生成されたスタブが、十分なコンテキストを得た際に自動的に「要約」を生成し、タグを `#未審査` から `#要確認` 等へ移行させるトリガーの定義が必要。
- **多言語対応**: 英語の専門用語と日本語の解説のバランス。現状は「英語表記優先、日本語解説」を基本とするが、エイリアス機能を使って両方の言語で検索可能にすることを徹底する。
- **視覚的リッチ化**: Mermaid.js 等を用いた図解の自動生成の導入を検討。
